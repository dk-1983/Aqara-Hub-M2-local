# Установочный комплект 4VRS M2 Local

Это **этап 2**: установка приложения на подготовленный хаб. Root-доступ и однократный загрузочный хук описаны отдельно в [этапе 1](../HARDWARE_SETUP.md). Пакет содержит все компоненты надстройки и не устанавливает зависимости из интернета. Для чистой установки приложения не нужно очищать заводскую базу датчиков.

Комплект предназначен для **HM2-G01 / lumi.gateway.agl001, RTL8197F, ПО 4.1.6_0018.0650** с уже полученным root-доступом через UART. Получение root, первоначальная активация заводского хаба и аппаратное восстановление не автоматизированы. Другие ревизии и версии требуют исследования.

Две независимые операции:

1. Однократно добавить минимальный хук автозагрузки в собственный заводской rootfs.
2. Установить приложение в `/data/aqara-panel`. Последующие обновления приложения не меняют rootfs.

Пакет приложения содержит веб-сервер, MQTT-мост, Discovery и супервизор. Пароли, MQTT-настройки, MAC, HomeKit-коды и Zigbee-база в него не включаются. При первой установке создаётся индивидуальный пароль; существующая идентичность и настройки сохраняются.

## Сборка приложения на компьютере

Готовый пакет: [Releases](https://github.com/dk-1983/Aqara-Hub-M2-local/releases). Скачайте `4vrs-m2-0.4.1.tar` и соседний `.tar.sha256` (не автоматически созданный GitHub архив Source code). Сверьте SHA256 на компьютере: `sha256sum 4vrs-m2-0.4.1.tar` в Linux или `Get-FileHash .\4vrs-m2-0.4.1.tar -Algorithm SHA256` в PowerShell. После этого переходите к разделу «Если хук уже установлен» либо к разделу установки хука ниже.

v0.4.1 опубликована как первый релиз; поддержка ограничена исследуемой платформой. 4 октября 2026 на исследуемом M2 проверены веб-обновление 0.4.0 → 0.4.1 и чистая установка пакета 0.4.1 из GitHub при отсутствии `/data/aqara-panel`. Создан новый пароль, авторизация работает, видны все пять прежних Zigbee-устройств без повторного сопряжения. После теста восстановлены настройки, оба MQTT-подключения и передача событий восстановились. Root и хук уже присутствовали; подготовка чистого второго хаба не проверялась.

Из корня репозитория, Python 3.10+ и Go из go.mod или новее:

```sh
python -m unittest discover -s installer -v
python installer/build_release.py --go go
```

`--go` может указывать полный путь к Go. Скрипт выполняет Go-тесты и vet, собирает Linux/MIPS little-endian softfloat, проверяет архитектуру ELF и создаёт `dist/4vrs-m2-<версия>.tar` плюс SHA256. Архив намеренно без сжатия: распаковка не требует xz и большого объёма RAM. Собирайте в новом `--output`, если архив этой версии уже существует.

## Обновления после первой установки

Начиная с 0.4.0 используйте страницу `/maintenance`: загрузите .tar, вставьте его SHA256, проверьте версию и подтвердите установку. Пакет собирается тем же `build_release.py`. Пароль, настройки MQTT и датчики сохраняются; старая версия остаётся для автоматического возврата при сбое. Нужен HTTP-порт 80 и свободное место размером с пакет плюс 2 МиБ. Получение root и первый запуск этой функции по сети не выполняются: первая установка — через UART.

## Если хук уже установлен

На хабе не нужен Git, Python или Go. Для передачи релиза можно временно раздать **только каталог с публичным пакетом** с компьютера. Например, из каталога, содержащего `.tar` и `.tar.sha256`, запустите Python на компьютере:

```sh
python -m http.server 8000 --bind <LAN-IP-компьютера>
```

В root-консоли хаба (замените адрес компьютера; для примера используется версия 0.4.1):

```sh
cd /data
wget -O 4vrs-m2-0.4.1.tar http://<LAN-IP-компьютера>:8000/4vrs-m2-0.4.1.tar
sha256sum 4vrs-m2-0.4.1.tar
```

Сравните результат с `.tar.sha256` из GitHub. Штатная утилита хаба **не поддерживает `sha256sum -c`**. Только при совпадении суммы распакуйте архив; убедитесь, что `/data/4vrs-m2` не содержит предыдущей установки:

```sh
tar -xf 4vrs-m2-0.4.1.tar
```

После успешной распаковки удалите только скачанный `.tar`, чтобы не держать на маленьком `/data` две копии пакета, и остановите временный HTTP-сервер компьютера. При недостатке места остановитесь и сохраните прежние резервные версии вне хаба; не удаляйте штатные каталоги Aqara. Затем перейдите в `/data/4vrs-m2` и выполните проверки ниже. Передача по локальному HTTP не заменяет сверку SHA256.

Передайте архив в отдельный временный каталог на `/data`, сравните его размер и SHA256 с файлом на компьютере. Распакуйте `tar -xf <архив>`. После успешной проверки и распаковки сам архив можно убрать с хаба для освобождения места. Каталог пакета должен оставаться отдельно от `/data/aqara-panel`.

Через root UART, из распакованного каталога:

```sh
sh install.sh check
sh install.sh install <IP-хаба>
```

IP нужен при первом создании идентичности. При обновлении можно опустить. `check` ничего не устанавливает и не останавливает. Проверяются модель, CPU, версия, UBIFS, контрольные суммы пакета и место. `install` также требует хук, отсутствие незавершённой транзакции и намеренно установленного маркера отключения.

Установщик готовит новый бинарник отдельно, делает одну локальную копию прежнего приложения и конфигурации (`install-backup`), останавливает только свои процессы, заменяет приложение и запускает супервизор. Проверяет ответ HTTP 401 без пароля. Это проверка запуска защищённой панели, **не проверка доставки MQTT в HA**. При ошибке запуска пытается вернуть прежний бинарник и супервизор; при невозможности безопасной остановки оставляет отключённый автозапуск для разбора по UART. После сбоя питания автоматическое завершение транзакции не обещается: `install-incomplete` сохраняется для ручного разбора.

Логин `admin`, начальный пароль — в `/data/aqara-panel/panel-password.txt`. Сохраните его в своём менеджере паролей и смените через панель. Файл с начальным паролем не обновляется при смене через UI. Установщик не печатает пароль и не меняет пароль root.

Откройте `http://<IP-хаба>`, настройте MQTT и включите Discovery. Проверьте реальные события, затем обычную перезагрузку и восстановление связи с HA. Перед следующим обновлением сохраните `install-backup` вне хаба и удалите только эту проверенную копию. В маленьком `/data` нельзя бесконечно хранить версии бинарника.

## Если хука ещё нет

Это отдельная операция записи rootfs. Нужны проверенные **вне хаба** копии всех MTD-разделов с совпадающими SHA256 и рабочий способ восстановления по UART. Копии NAND здесь означают чтение с ECC без OOB; это не универсальные образы для программатора. Не используйте заводские или пользовательские разделы другого хаба.

Сборщик работает в Linux/WSL с `squashfs-tools` 4.5.1; ему не нужны root-права. Он принимает только полный 16 MiB дамп проверенной заводской версии с известным SHA256. Даже совпадающее название версии при другом содержимом не разрешает прошивку.

```sh
python3 installer/build_hook.py /private-backups/mtd7-rootfs_2.bin /private-output/m2-hook
```

Можно задать `--unsquashfs` и `--mksquashfs`. Используется pseudo-file, сохраняющий права, владельцев, устройства и ссылки без распаковки на Windows NTFS. Сборщик сравнивает все записи до/после: допускается только добавление хука в `etc/init.d/rcS`. Создаются проверенный SquashFS, пакет штатного `fw_update`, отчёт и скрипт установки. Выходной каталог содержит заводские файлы и должен оставаться приватным; **он не входит в публичный архив приложения**.

Передайте в отдельный каталог хаба три файла: `rootfs-hook-update.bin`, `hook.env`, `flash_hook.sh`. Сравните SHA256 с компьютером. Затем:

```sh
sh flash_hook.sh check
```

Проверяются исполняемый файл штатного updater, таблица разделов, текущий rootfs целиком, оба банка и отсутствие ожидающей смены банка. Если банк невалиден, штатный updater может затронуть оба — скрипт откажется продолжать. При уже установленном хуке также откажется: обновлять rootfs повторно не требуется.

Когда резервные копии и UART-восстановление действительно готовы, явный режим записи:

```sh
sh flash_hook.sh apply-with-backup-and-uart
```

Скрипт не может проверить наличие аппаратного восстановления и резервных копий на другом компьютере: выбор режима означает подтверждение этих условий. После `fw_update` проверяются его журнал, SHA256 независимого чтения записанного банка и выбор следующей загрузки. Ненулевой код или ошибка проверки означает: **не перезагружать**, сохранить вывод UART и разобраться. Нулевой код самого `fw_update` недостаточен. Скрипт сам не перезагружает хаб.

После успешной проверки: `sync; reboot`. Убедитесь в запуске штатных служб и нового банка через `boot_ctrl show` и `/proc/cmdline`, затем установите приложение описанным выше способом. Файл пакета rootfs после сохранения всех результатов можно убрать с хаба.

Прежний банк остаётся резервным при прошедших проверках, но автоматическое восстановление не гарантируется. Заводской `boot_ctrl` не имеет команды выбора банка; восстановление прежнего банка — отдельная UART-процедура. Для проблем только с приложением достаточно `autostart.disabled`, без записи NAND.

## Датчики и расширение Discovery

Основная задача — передавать подтверждённые данные в стандартную MQTT-интеграцию HA. M2 — отдельное устройство, датчики связаны с ним через `via_device` и сохраняют собственные комнаты и карточки.

Текущие декодеры: P1 `lumi.motion.ac02`, старый датчик движения `lumi.sensor_motion.aq2`, протечка `lumi.sensor_wleak.aq1`. Для `lumi.flood.agl02` есть ветка декодера, но физического испытания T1 пока не было. Неизвестные модели сохраняются в списке устройств, исходные сообщения передаются в `<prefix>/zigbee/send`; автоматически угадывать сущности по номерам ресурсов нельзя.

Новая модель добавляется после записи её реальных событий: точный model, ресурс, тип значения, единицы/масштаб, поведение report/heartbeat и крайние значения. Затем добавляются соответствие в `discovery.go` и тест с обезличенным сообщением. Команды управления проверяются отдельно от чтения. Поддержка в HA не требует добавлять в веб-панель каждую настройку каждого датчика. Внешние MQTT-команды управления сейчас не принимаются.

## Границы проверки

Проверено 2026-10-01:

- Сборщик из исходного дампа воспроизвёл **побайтно** SquashFS и пакет, ранее успешно записанные и загруженные на нашем HM2-G01. Сравнены все 2713 записи, изменён только `rcS`.
- Go-тесты и vet; проверки формата ELF, метаданных rootfs и контрольной суммы пакета.
- В Linux с настоящим процессом панели и временными каталогами: первая установка, обновление, сохранение авторизации и конфигурации, отказ для другой модели/испорченного пакета, возврат предыдущего приложения при неудачном запуске.
- В модели NAND на обычных файлах: запрет записи при невалидном банке или ожидающей смене банка, независимое чтение после записи, отказ при ложном `Success` и несовпадающем содержимом.

Повторить проверку жизненного цикла в Linux/WSL можно с нативной Linux-сборкой панели:

```sh
cd webpanel
go build -o ../build/panel-test-native .
cd ..
python3 installer/test_lifecycle.py build/panel-test-native
python3 -m unittest discover -s installer -v
```

Хук, перезагрузка и супервизор ранее испытаны на одном HM2-G01. Чистая установка приложения на этом же хабе теперь проверена отдельно: опубликованный установщик запущен без изменений, прежний каталог приложения временно перенесён, создана новая идентичность. Полный путь подготовки второго заводского хаба не проверялся; Linux-тесты подменяют проверки аппаратуры и пути временными файлами. Повторная прошивка рабочего M2 ради проверки установщика не выполнялась. Работа текущего экземпляра не доказывает совместимость со всеми M2.
