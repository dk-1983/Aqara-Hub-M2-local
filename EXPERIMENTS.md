# Исследование M2: воспроизводимые наблюдения

## Дополнение: установка опубликованного релиза, 4 октября 2026

На том же HM2-G01 проверено веб-обновление 0.4.0 → 0.4.1 из GitHub Releases. API сообщил `success`, оба MQTT-подключения восстановились, от P1 получены движение и освещённость 40 лк.

Затем отдельно проверена чистая установка **приложения**. До остановки моста сохранена приватная копия его файлов вне хаба и сверены контрольные суммы. Старый каталог `/data/aqara-panel` перенесён; неизменённый `install.sh` из опубликованного пакета запущен при отсутствии этого каталога. Root-доступ и загрузочный хук уже были подготовлены, повторной записи rootfs не выполнялось.

Установщик создал новую идентичность и запустил панель 0.4.1. Прежний пароль отклонён, новый принят. Новая панель получила из штатного хаба тот же набор пяти DID без повторного сопряжения; MQTT-мост по умолчанию выключен до настройки. После проверки восстановлены прежние авторизация, MQTT-конфигурация и настройки устройств; SHA256 этих трёх файлов совпали с резервной копией. Оба MQTT-подключения и передача событий возобновились.

База Zigbee не удалялась и не заменялась. Тестовые каталоги убраны, предыдущая версия приложения сохранена отдельно для отката. Это подтверждает второй этап установки на уже подготовленной исследуемой платформе, но не полный заводской путь на другом M2.

Дата испытаний: 30 сентября 2026. Одна конкретная плата LM18-GWMM V1.1.0, корпус HM2-G01, фактическая модель lumi.gateway.agl001, штатное ПО 4.1.6_0018.0650.

## UART и резервная копия

UART: 38400, 8N1, без аппаратного управления потоком, логические уровни 3,3 В. На исследованной плате четырёхконтактная площадка находится между USB-A и электролитическим конденсатором. Считая от квадратной площадки: 1 — не подключать; 2 — GND; 3 — TX хаба; 4 — RX хаба. Перед подключением к другой ревизии проверьте плату и уровни, не подавайте питание с адаптера.

Для получения recovery-shell использовались опубликованные инструменты [AqaraM1SM2fw](https://github.com/niceboygithub/AqaraM1SM2fw). Промежуточный monitor загружался в RAM. Заводские bootloader, kernel и rootfs не переписывались. Полную процедуру получения root проект пока не автоматизирует.

Сохранены девять MTD-разделов общим объёмом 120717312 байт; SHA256 каждой копии сравнен с независимым чтением на хабе. /data при снятии дампа не был смонтирован. Это ECC-корректированные логические MTD-данные **без OOB**, не полный физический NAND-образ для программатора. Заводские дампы не публикуются.

После резервного копирования включена UART-консоль и установлен индивидуальный пароль admin (UID 0). Вход проверен после штатной перезагрузки. SSH/Telnet для работы надстройки не требуется.

## Откуда берутся люксы P1

В диагностике HomeKit Device для P1 не было light-сервиса. Сам HA умеет работать с освещённостью по HomeKit, но хаб не публиковал это свойство для исследуемых датчиков.

Во внутреннем MQTT M2 получен отчёт на zigbee/send:

```json
{
  "cmd": "report",
  "did": "lumi.EXAMPLE",
  "params": [
    {"res_name": "3.1.85", "value": 1},
    {"res_name": "0.4.85", "value": 40},
    {"res_name": "0.3.85", "value": 40}
  ]
}
```

DID заменён примером. Значения 11 и 40 лк действительно получены при движении. В heartbeat того же устройства встречалось 0.3.85=0; при последующей реализации HA-сущности нельзя без проверки трактовать каждый heartbeat как свежее измерение.

## Добавление датчика локально

Исходники AqaraGateway показывают команду сопряжения. Через внутренний MQTT на zigbee/recv отправлено:

```json
{"cmd":"write","did":"lumi.0","id":49101,"params":[{"res_name":"8.0.2109","value":60}]}
```

Это открывает 60-секундное окно. Свободный датчик затопления переводится в режим сопряжения кнопкой. Для исследуемого датчика Aqara — удержание примерно 5 секунд до синего мигания.

Полученная последовательность:

1. 8.0.2109: write_rsp с error_code=0.
2. 8.0.2110: обнаружен новый MAC.
3. 8.0.2111: разрешение добавления, code=0. Его инициировала штатная часть, не наш скрипт.
4. 8.0.2084: добавлен lumi.sensor_wleak.aq1, version=6, Zigbee 1.2.
5. 8.0.2109=0: штатная часть закрыла окно сопряжения.

Первый датчик добавлен при обычном подключении. Второй, с другим MAC, — при запрете внешней маршрутизации. В обоих случаях новое устройство появилось в HomeKit Device.

## Проверка без интернета

Временные маршруты unreachable 0.0.0.0/1 и unreachable 128.0.0.0/1 перекрыли внешние IPv4-адреса, сохранив более специфичный LAN-маршрут. Рабочего внешнего IPv6-маршрута не было. Откат маршрутов был запланирован заранее на 600 секунд.

Перед и после сопряжения ip route get для внешних адресов возвращал Network is unreachable. Локальный MQTT, Ethernet и HomeKit оставались доступны. Промежуточное разрешение 8.0.2111 появилось и в этих условиях.

Это подтверждает локальное добавление данного типа датчика в уже настроенный хаб. Не проверены первоначальная активация после factory reset, удаление аккаунта, работа любых производителей, длительная автономность и штатная загрузка без WAN.

## Проверка веб-панели

- Linux/MIPS little-endian softfloat, Go 1.27.1, без внешнего runtime.
- Финальная сборка порядка 8,9 МБ; RSS около 9,5 МБ после функциональных проверок. Это измерение конкретного сеанса, не максимальный расход памяти.
- HTTPS с индивидуальным сертификатом проверен с доверенным локальным сертификатом.
- Неавторизованный API возвращает 401.
- Заводские сведения и effective model прочитаны с самого хаба.
- MQTT CONNECT выполнен к штатному брокеру. Мост включён/выключен через браузер в loopback-тесте с отдельным префиксом.
- Передача JSON проверена также автоматическим тестом с двумя независимыми MQTT-брокерами.
- Пароль панели изменён, старый отвергнут, новый принят. После возвращения исходного значения PBKDF2-формат сохранён. Вход проверен после перезапуска процесса.
- Копия root-пароля сохранена через HTTPS API; показ и скрытие проверены в браузере. Она отсутствует в status/about.
- Ethernet временно переведён DHCP → static с тем же IP, маской и шлюзом. Подтверждение не отправлялось. Через 90 секунд независимый процесс вернул DHCP даже после перезапуска панели.
- При новой DHCP-аренде сервер выдал другой шлюз; после теста исходный маршрут был восстановлен вручную. DHCP определяется сервером, поэтому возврат в DHCP не гарантирует побитно те же сетевые значения.
- Проверены настольная и мобильная ширина страницы; ошибок JavaScript нет.

Автозапуск надстройки и постоянное применение сетевых настроек после загрузки ещё не реализованы. Изменение на другой IP/подсеть и ветка подтверждения сети на реальном хабе пока не проверены.
